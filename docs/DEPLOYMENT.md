# Render deployment

The user's free test deployment is now live. Use [RENDER-DEPLOYMENT.md](RENDER-DEPLOYMENT.md) for its actual URLs, credentials-file location and verified checks. The instructions below describe provisioning a separate environment.

Use familyguard/ as the repository root so render.yaml's relative rootDir paths resolve. Create your own Git repository and push these sources. Create a Render Blueprint from render.yaml. The blueprint currently provisions a free testing web service, a static React site, and a free managed PostgreSQL database in Singapore. Free services can sleep and free databases expire after 30 days. Review current plan availability/costs in Render before provisioning. No Render account or production secrets have been supplied in this workspace; nothing is deployed by generating these files.

Set ADMIN_EMAIL and a random ADMIN_PASSWORD of at least 14 characters. Generate JWT_SECRET and DATA_ENCRYPTION_KEY **separately** using a cryptographically secure generator: each is base64 of 32 random bytes. In PowerShell, `[Convert]::ToBase64String([System.Security.Cryptography.RandomNumberGenerator]::GetBytes(32))` works on modern PowerShell; otherwise use your password manager or `openssl rand -base64 32`. Store them in Render's secret environment fields. Do not share logs containing secrets. Keep the encryption key backed up separately; losing it makes existing event payloads unreadable. Key rotation requires re-encryption, not simply changing the variable.

Database host/port/name/user/password are linked from Render. Spring constructs the JDBC URL automatically. For an external managed database, override DATABASE_URL with a JDBC URL (not postgres://), e.g. `jdbc:postgresql://HOST:5432/familyguard?sslmode=verify-full` plus a trusted provider CA as needed. DATABASE_USER and DATABASE_PASSWORD remain separate. Use Render's private network for its database and restrict public DB access. Flyway applies the canonical migration under backend/src/main/resources/db/migration; database/ contains its review copy. Do not run both manually against the same DB.

Set FRONTEND_ORIGIN to the exact HTTPS React origin, no trailing slash, e.g. https://familyguard-YOUR-SLUG.onrender.com. Multiple permitted origins may be comma-separated. Set frontend VITE_API_URL to the exact HTTPS backend origin, e.g. https://familyguard-api-YOUR-SLUG.onrender.com. Vite variables are build-time: redeploy frontend after changing. Use the actual Render-assigned URLs, not example names. Reflect those URLs in Android local.properties and rebuild the APK. SECURE_COOKIES must remain true in production.

Render terminates HTTPS and forwards traffic to the backend PORT. The backend respects forwarded headers, uses HTTPS-only cookies and only explicitly allowed CORS origins. The public health check is `/actuator/health`; it includes database readiness but never exposes credentials/details. Other actuator endpoints are not exposed. The backend Dockerfile compiles and executes tests, then runs a non-root Java 21 JRE. Render's ephemeral filesystem is not used for persistent data.

React routes are rewritten to index.html. Deploy static headers from render.yaml. For custom domains, keep parent frontend and API under the same registrable domain (e.g. app.example.com / api.example.com) so refresh cookies are not blocked by third-party-cookie restrictions. Cross-origin requests use credentials, explicitly allowed origins and Origin validation on cookie-based auth routes. HTTPS is still mandatory for the APK.

The service should remain a single backend instance: WebSocket tickets, connection sets and rate limits are intentionally in memory for this one-family deployment. Database locking and uniqueness protect single-device pairing. Browser refresh cookies rotate; logging in again invalidates previous access-token sessions. Access tokens live in React memory. No public registration or multi-family tenancy is provided.

Android retries timeouts, 429s and 5xx with WorkManager exponential backoff. React uses a 45-second request timeout with explicit retry guidance. WebSocket reconnects and 60-second API polling recover after service restarts. Offline alerts use a 45-minute missing-sync threshold (not instant phone connectivity detection); the threshold should exceed expected WorkManager delays. Scheduler jobs and WebSockets cannot operate while a service is asleep. Free plans, if deliberately selected, cannot promise continuous alerts or uptime. Backend startup fails rather than silently serving with an unavailable DB; health checks and platform restart policy handle recovery.

Use managed PostgreSQL backups with a tested restoration procedure. Account/device deletion affects the live database; provider backups expire on their own configured schedule. Audit logs contain action names only and expire after 90 days. Activity is retained 1–90 days; location history also has a separate 1–90 day cap (minimum of both settings). Cleanup runs hourly. Server event receipts remain 91 days to reject replayed old events. Backups, physical devices, keystore custody, incident response and restore testing are operator responsibilities.

Parent alerts use the existing authenticated WebSocket with a durable PostgreSQL catch-up feed and the native Parent Android receiver. The user starts a visible foreground connection and Android NotificationManager displays approved metadata while connected, including when the web dashboard is closed. No Firebase or external push provider is used. Deploy the V2 migration/backend and updated React Settings before registering the parent phone. Android/Doze, process stops, network loss and Render sleep can delay delivery. See [REALTIME-NOTIFICATIONS.md](REALTIME-NOTIFICATIONS.md).
