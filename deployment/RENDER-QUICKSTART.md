# Publish FamilyGuard on Render

1. Push **the contents of familyguard/** to a private GitHub repository, with render.yaml, backend/, frontend/ and android-app/ at its top level. Do not push the parent folder containing .tools/ or any local environment files. A Git repository inside familyguard/ avoids the root-directory mismatch.
2. Sign in to https://dashboard.render.com and connect that GitHub repository. Choose **New → Blueprint**, select the repository, select main, and use **render.yaml** as the Blueprint path.
3. Review the proposed resources before deploying: familyguard-db (PostgreSQL), familyguard-api (Docker web service) and familyguard (static React site). The Blueprint is configured for the free testing setup you selected. Free databases expire after 30 days and free web services can sleep. Do not upgrade plans unless you want the additional charges. Plan changes belong in the Blueprint, not just the dashboard.
4. Provide ADMIN_EMAIL, ADMIN_PASSWORD (at least 14 characters), JWT_SECRET (base64 of 32 random bytes), DATA_ENCRYPTION_KEY (a separate base64 value for 32 random bytes), FRONTEND_ORIGIN and VITE_API_URL when prompted. Database credentials are wired automatically. SECURE_COOKIES stays true. Never use the literal example values.
5. For a guided secrets setup, after the actual Render HTTPS origins are known run `deployment/prepare-render.ps1 -AdminEmail YOUR_EMAIL -FrontendOrigin https://YOUR_FRONTEND.onrender.com -ApiOrigin https://YOUR_BACKEND.onrender.com`. The script creates ignored deployment/.private/backend.env and frontend.env, never overwrites previous keys, and does not print secrets. Read these files locally and import the corresponding values into Render Environment settings. Keep the generated ADMIN_PASSWORD privately and back up DATA_ENCRYPTION_KEY. If the Blueprint requires values before URLs are assigned, generate your keys locally with your password manager, use temporary example origins only for that initial provisioning, then replace both origin variables with the actual assigned URLs immediately.
6. Deploy the Blueprint and monitor the backend build/migration logs. Check **https://YOUR_BACKEND.onrender.com/actuator/health** returns UP. The API has no dashboard at its root URL; use the separate frontend URL.
7. If Render adds a suffix to service names, update backend FRONTEND_ORIGIN to the exact frontend HTTPS origin, and frontend VITE_API_URL to the exact backend origin. Do not add a trailing slash or /api. Redeploy backend and rebuild frontend after changes. Never loosen CORS to a wildcard to fix an origin typo.
8. Open the frontend, sign in with the configured parent account, refresh the page to test the refresh cookie, generate a pairing code, and review privacy settings. With no paired Android phone, the correct result is an empty dashboard.
9. Update android-app/local.properties with the same actual HTTPS API/web URLs, rebuild the APK, and install it on both phones. The existing compiled APK contains placeholders and cannot pair with your deployed backend.

If a browser blocks cross-site refresh cookies on separate onrender.com subdomains, use frontend/API custom domains under the same registrable domain. Do not store refresh tokens in browser localStorage as a workaround.

Database external access is denied by ipAllowList: []; the backend uses Render's internal database hostname. Runtime data belongs in PostgreSQL; Render's web-service filesystem is ephemeral. The Android app stays on your phones; only React, Spring Boot and PostgreSQL are deployed to Render.

Sources: [Render Blueprint setup](https://render.com/docs/infrastructure-as-code), [Blueprint specification](https://render.com/docs/blueprint-spec), [free-tier limitations](https://render.com/docs/free).
